# 冲突与不确定性

## 已采用的路径解释

`PROMPT.md` 的旧示例曾出现嵌套输出名 `bioinformatics-linear-script-style/review`，
但当前用户明确指定目标为 `<SKILL_ROOT>`。本轮采用最新、
更具体的指令，直接写入：

`<SKILL_ROOT>/review/`

没有创建额外嵌套仓库。

## 人工确认后的处理

2026-07-30 已确认 API-like 文件作为反例、validation holdout 在初始规则完成前隔离、
Mono principal-curve 脚本加入正式 holdout，并确认两个 GRN 脚本具有 README 未说明的
特殊地位。以下各节保留原始冲突及 Phase 2 的处理方式。

### 1. 章节标题没有唯一语法

语料同时出现普通 `##`、带分隔线的标题，以及 `[检查点]`、`[决策点]`、
`[专家经验]`。它们支持“用语义章节表达主线”，但不足以支持唯一标题模板。

建议：Phase 2 规定标题应说明目的或判断，不强制一种装饰语法。

### 2. “减少函数”与“合理复用”的边界

大部分主分析是线性的，但 20 个脚本定义了局部函数。函数既有明显合理用途
（逐基因模型、bootstrap、重复绘图、批量样本），也有把核心分析整体隐藏起来的
边界案例。

已确认采用：不设函数数量上限；要求每个新函数回答“是否显著减少重复或隔离窄技术细节”，
否则内联。

### 3. API-like 文件是否作为反例

`04-grn/scripts/02-regulon_activity_score.R` 更像可复用 API，而不是一次性分析脚本。
如果把它作为主样例，可能会把 Skill 拉回工程化封装。

已确认：将其作为“分析脚本与库代码的边界反例”，不从中提炼主风格。

### 4. README 与实际脚本不完全一致

- `03-integration/README.md` 主要描述环境，几乎不提供工作流证据。
- `06-lr-pairs/README.md` 提到 `05-cellchat-stage-compare.R`，实际存在
  `05-cellchat-stage-compare-LRnum.R` 与
  `05-cellchat-stage-compare-weight.R`。
- `04-grn/README.md` 的部分命令与脚本目录/工作目录关系不完全清楚。

建议：脚本清单以实际允许范围内的文件为准；README 只提供低优先级上下文。

### 5. 重复编号不能证明 legacy

`07-trajectory/scripts/04-4-lineage-pcurve-CLP.R` 与
`07-trajectory/scripts/04-4-lineage-pcurve-pDC.R` 使用相同编号。文件名和修改时间都
不能证明其中一个已废弃。

建议：两者均标记“状态不确定”，不要删除、降级或宣称 legacy。

### 6. 参数位置不统一

有些脚本把参数集中在开头，有些把参数放在使用点附近。两种方式都能保持参数可见。

建议：优先“在首次使用前容易定位”，不强制所有参数集中成 config 区，更不引入配置层。

### 7. `View()` 与批处理存在冲突

少量 R 脚本使用 `View()` 做人工检查，多数脚本依赖 `head()`、`summary()`、表格或图。

建议：把交互式检查标成可选；最终可重跑脚本应提供非交互检查。

### 8. 输出目录和命名不统一

语料使用 `data/`、`output/`、figure 子目录和多种路径变量名。部分脚本主动建目录，
覆盖保护和结束提示并不普遍。

建议：要求输入输出路径显式、产物角色清楚；暂不学习唯一目录结构、变量名或覆盖策略。

### 9. `setwd("scripts")` 是高频但可能只属于当前项目

该做法在语料中很稳定，却可能依赖 sc06 的执行方式。通用 Skill 若把它设成硬规则，
会与其他项目的仓库根目录执行约定冲突。

建议：Phase 2 把工作目录当成需要先确认的项目约定，而非全球默认。

### 10. 环境细节已被排除

允许脚本内偶然出现 Pixi 命令或 `.pixi` 路径。本轮只识别其为环境特例，没有把它们
纳入候选模式。没有读取 Pixi manifest、lockfile 或环境目录。

建议：最终 Skill 明确“不从分析脚本复制机器特定环境路径”。

### 11. 05 阶段上游不完整

`05-from-pathway-to-program/scripts/` 在允许语料中从 `02` 开始；cNMF 结果如何生成
不在本轮证据中。

建议：只归纳“解释已有 program 结果”的风格，不假设完整 cNMF pipeline。

### 12. 07 阶段的平行脚本是否应继续独立

多个 lineage 脚本结构高度相似。合并成通用函数会减少重复，但也可能隐藏每条 lineage
真正不同的 root、terminal、基因和 cutoff。

建议：默认保留独立脚本与少量重复；只有在共同修改已经频繁漂移时，才提取最小技术函数。

### 13. “短提纲”与禁止 spec/plan 的边界

用户要求脚本前先做简短思考，同时保留：

`You may use superpowers, but do not write any spec or plan.`

已确认采用该边界：可以在对话中用几句话说明问题、输入、关键决定和预期输出；不得为此创建
独立 spec、plan 文件或庞大的前置工程流程。

### 14. “遵循第一性原理”如何变成可检查行为

仅在 `AGENTS.md` 写一句口号不足以指导脚本。候选可检查行为包括：

- 先明确研究问题和可观察输入。
- 区分数据事实、方法假设与生物学判断。
- 关键参数给出当前任务的理由。
- 用中间检查和输出验证推理链。
- 不因为已有模板存在就跳过问题重构。

Phase 2 同时保留固定句子“遵循第一性原理”和上述行为解释。

### 15. 两个 GRN 脚本的特殊地位尚未分类

用户确认 `04-hypothesis_driven_partII.R` 与
`06-screen_TFs_for_given_target.R` 有 README 未说明的特殊地位，但尚未说明具体角色。

处理：标记为 `special-status-unclassified`；不宣称 legacy、不作为普通未入选样例，
也不依赖它们形成规则。待具体角色明确后再更新范例索引。

## 暂定但未升级为规则的判断

- R 是主分析语言，Bash/Python 保持窄职责。
- 允许少量重复以换取局部可读性。
- 不为单个脚本引入 class、复杂 config、跨文件 wrapper 或通用框架。
- 外部 API 视为不透明边界。
- validation holdout 在规则草案完成前不参与学习。

这些判断已在 Phase 2 采用；具体阶段例外仍以验证结果为准。

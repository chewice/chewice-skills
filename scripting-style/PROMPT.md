# 5. 核心学习目标

## 5.1 线性生物学分析主线

最重要的目标是学习脚本如何从上到下表达完整的分析过程。

优先学习类似以下结构：

```
说明本脚本的分析目的
→ 加载必要依赖和API
→ 定义输入、输出和主要参数
→ 读取数据或分析对象
→ 检查数据结构和样本构成
→ 执行数据筛选或预处理
→ 执行核心分析
→ 查看关键中间结果
→ 进行必要的诊断或敏感性检查
→ 整理统计结果
→ 生成图形
→ 保存表格、图形或对象
→ 汇总本步骤完成情况
```

这里的“可读性”是指：

> 研究者能够顺着脚本阅读，理解数据如何一步步转化为统计结果和生物学结果。

不是指通过大量函数、类、模块和抽象层将分析过程隐藏起来。

------

## 5.2 禁止过度工程化

不要把历史脚本自动改造成：

- 大量类；
- 多层对象封装；
- 复杂配置框架；
- 依赖注入；
- 插件系统；
- 工作流引擎；
- 通用软件包；
- 大量微型函数；
- 为形式整洁而进行的过度模块化。

不得默认将整个脚本改写成：

```
main <- function() {
  config <- initialize_config()
  data <- load_data(config)
  result <- run_analysis(data, config)
  save_results(result, config)
}
```

如果这种封装会隐藏：

- 样本筛选；
- 细胞筛选；
- 分组定义；
- 模型设计；
- contrast；
- root选择；
- marker判断；
- 参数诊断；
- 中间结果检查；

则不应采用。

统计设计和生物学决策应尽可能明确地保留在线性主线中。

# 6. 局部辅助函数的学习规则

`scripts/` 中可能包含作者自行编写的小函数。

需要学习这些函数的：

- 命名方式；
- 注释方式；
- 定义位置；
- 参数组织；
- 返回值方式；
- 在主线中的调用位置；
- 用于减少哪类重复代码；
- 是否使主线更容易阅读。

适合学习为局部函数模板的内容包括：

- 重复的图形保存；
- 简单输入检查；
- 结果表整理；
- 重复绘图操作；
- 少量格式转换；
- 重复的批量调用；
- 技术性而非生物学决策性的辅助操作。

通常不应封装的内容包括：

- 研究对象筛选；
- 样本纳入排除；
- 细胞类型选择；
- 模型设计；
- 协变量定义；
- 对比矩阵；
- 聚类参数选择；
- root选择；
- marker判断；
- 核心统计分析；
- 关键生物学解释步骤。

## 6.1 不建立公共函数库

本次任务不得创建：

```
lib/
utils/
package/
公共R包
公共Python包
公共Shell函数库
```

不得把所有小函数集中到 `utils.R`、`helpers.R` 或类似文件。

## 6.2 函数模板的形成条件

只有满足以下条件的小函数，才可以被记录为“局部辅助函数模板”：

- 在多个范例脚本中重复出现；
- 或虽然只出现一次，但具有明显代表性；
- 职责明确；
- 不包含项目专属路径；
- 不隐藏核心生物学逻辑；
- 适合直接放在新脚本内部；
- 能提高线性主线的可读性。

模板只用于在新脚本内部生成局部函数，不作为公共API调用。

# 7. 参数学习规则

需要学习：

- 参数通常放在脚本什么位置；
- 参数如何分节；
- 参数如何命名；
- 参数如何注释；
- 哪些参数集中定义；
- 哪些参数靠近使用位置；
- 参数如何记录到结果中；
- 参数调整后如何体现；
- 是否存在参数诊断或敏感性比较；
- 参数与输出文件如何关联。

不得把历史脚本中的具体数值直接泛化为新项目默认值。

例如，脚本中出现：

```
resolution <- 0.7
```

不代表未来所有项目都应使用 `0.7`。

应学习的是：

- `resolution` 在哪里定义；
- 为什么需要显式定义；
- 是否进行过多个值比较；
- 如何保存参数；
- 改变参数后哪些结果需要重新生成。

将参数大致区分为：

- 数据决定；
- 文献参考；
- 算法要求；
- 统计决策；
- 计算资源；
- 视觉展示；
- 敏感性分析；
- 项目专属。

但不要建立复杂参数管理系统。

# 9. 需要分析的脚本特征

对 `scripts/` 中的脚本重点观察以下内容。

## 9.1 文件头

- 是否说明脚本目的；
- 是否说明输入；
- 是否说明输出；
- 是否说明所属分析阶段；
- 是否说明运行方式；
- 是否说明依赖的上游结果。

## 9.2 分节方式

- 分节标题的格式；
- 分节编号；
- 一级与二级分节；
- 注释密度；
- 分节与分析步骤的对应关系；
- 是否按生物学问题划分，而不是只按编程结构划分。

## 9.3 依赖与API加载

- 包加载放在哪里；
- 是否抑制启动信息；
- API文件如何加载；
- API调用前后如何准备和检查数据；
- Python模块或Bash工具如何调用。

## 9.4 路径与输入

- 项目根目录如何处理；
- 输入路径如何组织；
- 是否使用相对路径；
- 是否集中定义输入；
- 是否检查输入存在；
- 如何读取 RDS、CSV、TSV、H5AD 或其他对象。

## 9.5 主线流程

- 分析步骤的先后顺序；
- 中间变量如何命名；
- 中间结果是否显式保留；
- 关键对象是否反复覆盖；
- 图形是否紧跟对应分析；
- 统计结果是否在保存前进行检查。

## 9.6 注释与说明

- 注释是解释“做什么”还是“为什么”；
- 哪些地方会解释生物学目的；
- 哪些地方会解释参数；
- 哪些地方会标记注意事项；
- 是否保留待调整项或探索性判断。

## 9.7 输出

- 表格、图形、对象的保存顺序；
- 命名风格；
- 文件前缀；
- 图形尺寸；
- 是否保存矢量图；
- 是否输出摘要信息。

## 9.8 R、Python、Bash之间的关系

- Bash如何调用R或Python；
- Python是否负责数据整理或批处理；
- R是否承担主要统计和绘图；
- 不同语言脚本如何交换文件；
- 执行入口位于哪里；
- 哪些模式属于语言特异，哪些属于全局共同风格。

# 11. 风格冲突处理

不同脚本可能存在不同写法。

发生冲突时，使用以下优先级：

```
同类分析中的代表脚本
>
同一阶段多个脚本反复出现的稳定模式
>
跨阶段共同出现的稳定模式
>
更能保持线性生物学主线的写法
>
单个脚本中的偶然写法
```

不得仅根据以下因素判断哪个写法更优：

- 文件修改时间更新；
- 文件更长；
- 函数更多；
- 看起来更工程化；
- 使用了更多外部包。

如果两种模式各有适用场景：

- 同时保留；
- 描述各自适用条件；
- 不强行统一。

如果无法可靠判断：

- 标记为待确认；
- 不写成强制规则。

# 20. 模板原则

模板只提供结构，不固定具体分析方法和参数。

## 20.1 R模板

`templates/linear-analysis.R` 应体现：

```
# 脚本说明

# 1. 加载依赖与指定API

# 2. 定义输入、输出与主要参数

# 3. 读取数据

# 4. 检查数据结构与样本构成

# 5. 必要的数据准备

# 6. 核心分析

# 7. 关键中间结果检查

# 8. 结果整理与可视化

# 9. 保存输出

# 10. 完成摘要
```

不得塞入与所有任务无关的复杂框架。

## 20.2 Python模板

重点体现：

- 清晰入口；
- 参数；
- 输入输出；
- 数据处理主线；
- 必要的局部函数；
- 与R或文件输出的衔接。

不得自动引入类。

## 20.3 Bash模板

重点体现：

- 调用顺序；
- 输入检查；
- 清晰命令；
- R/Python脚本调用；
- 错误退出；
- 进度输出。

不得发展为复杂工作流管理器。

## 20.4 局部函数片段

`local-helper-snippets.md` 只记录经过确认的局部辅助函数模式。

不得复制项目专属函数作为通用模板。

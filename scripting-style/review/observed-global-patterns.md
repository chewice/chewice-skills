# 全局候选模式

> 本文件记录 Phase 1 的观察，不是最终规范。每一项都需要结合候选样例、
> 反例和 validation holdout 再决定是否进入 Skill。

## 1. 以可顺序阅读的分析主线为骨架

大多数脚本从依赖和路径开始，随后加载输入、检查数据、执行分析、检查结果并保存输出。阅读者不需要跨多个本地模块才能找到主分析流程。

- 支持证据：7 个阶段都存在明显的自上而下执行链。
- 反例或边界：外部 API 通过 `source("../R/...")` 加载；这些 API 被当作不透明能力，而不是要求在脚本内展开。
- 初步判断：高置信度，可作为风格核心。

## 2. 参数和科学决定保持在调用附近

QC 阈值、PC 数、resolution、anchor 参数、lineage 的 root/terminal、筛选 cutoff、目标细胞和基因集通常直接写在脚本中或紧邻使用位置。

- 价值：读者可以从脚本判断“为什么得到这个结果”，而不必追踪配置系统。
- 边界：语料中的具体数值属于历史分析，不应复制为默认值。
- 初步判断：高置信度；应要求显式解释关键决定，而非要求固定参数。

## 3. 注释优先解释阶段、判断和原因

常见注释包括普通章节标题、`[检查点]`、`[决策点]`、`[专家经验]`，以及对参数选择或图形诊断目的的说明。

- 支持证据：annotation、integration、GRN 和 trajectory 尤其明显。
- 冲突：章节标记至少有三套写法，不能在 Phase 1 指定唯一语法。
- 初步判断：高置信度保留语义，低置信度统一格式。

## 4. 输入检查嵌入流程，而非另建验证框架

`head()`、`dim()`、`summary()`、`table()`、对象打印和诊断图直接出现在关键转换前后。

- 价值：检查与其保护的分析步骤相邻。
- 边界：`View()` 只在少量脚本中出现，适合交互探索，不适合作为批处理硬要求。
- 初步判断：高置信度要求关键检查；具体检查函数按数据类型选择。

## 5. 外部 API 的可见边界是“准备—调用—检查—保存”

顶层 `R/` API 的内部实现不在本轮语料范围内。脚本侧的稳定模式是：

1. 明确准备 API 所需对象和参数。
2. 在使用前加载 API。
3. 调用后检查返回对象或绘制诊断图。
4. 保存表格、图或对象。

初步判断：高置信度；不能据此推断或重写 API 内部。

## 6. 函数只在重复或窄技术任务中获得明显收益

局部函数常见于批量保存图、purity 计算、bootstrap、逐基因模型、基因集加载、单样本 CellChat 和重复绘图。

- 正向证据：函数减少重复技术噪声，同时主分析顺序仍可见。
- 反向证据：个别脚本把完整核心算法包进一个函数，阅读时需要进入函数体才能理解主线。
- 初步判断：应形成“减少函数封装和工程化”的约束，但不是函数禁令。若一个短函数不能显著减少重复、隔离技术细节或明确输入输出，就优先内联。

## 7. 允许少量重复来保持局部可读性

同类 lineage、stage comparison 和多个样本的脚本存在结构重复。重复使每个分析分支可独立阅读，也暴露了不同分支真正改变的参数。

- 风险：机械复制会造成漂移，例如相邻脚本的路径、标题或变量名不一致。
- 初步判断：允许有意义的局部重复；若重复已经妨碍一致修改，再考虑最小范围函数或循环。

## 8. 输出与分析步骤紧邻

绘图通常在数据变换或统计结果之后立即发生，并显式指定文件名、尺寸或分辨率；中间对象、结果表和最终图可分别保存。

- 冲突：`output_dir`、`out_dir`、`figure_dir`、`fn`、`plot_file` 等命名并不统一。
- 冲突：覆盖保护和完成提示并非普遍存在。
- 初步判断：保留“输出靠近产生它的步骤”和“输出路径显式”，暂不规定唯一变量名或统一覆盖策略。

## 9. 文件名和前序产物表达工作流顺序

数字前缀和 part/lineage/stage 后缀帮助表达执行顺序与分析分支。

- 边界：存在重复编号和 README 与实际脚本名不一致，编号不是充分的真值来源。
- 初步判断：Skill 可鼓励明确脚本角色和上游依赖，但不能只依靠文件名推断顺序。

## 10. 语言角色有清楚分工

- R：统计分析、生物学推断、诊断和可视化。
- Bash：外部命令参数、样本级执行和步骤编排。
- Python：窄范围格式转换。

初步判断：中高置信度。Skill 应保持语言原生、直接的写法，不把三种语言强行套进同一工程骨架。

## 11. 工作目录是高频惯例，但可能是项目约定

绝大多数 R 脚本显式设置工作目录，随后使用相对路径。

- 支持：当前语料内部高度一致。
- 风险：这是 sc06 项目的运行约定，不一定适合所有仓库。
- 初步判断：记录为项目级候选惯例，不在人工确认前升级为通用硬规则。

## 12. “先讲清问题，再写脚本”需要与轻量风格兼容

从语料中的目的注释、决策注释和顺序结构可支持一种轻量工作方式：写脚本前先用几句话说明研究问题、输入、关键决定和预期产物，再直接写线性代码。

- 这可以是对话中的短提纲。
- 不应演变为独立 spec、plan 文档或复杂脚手架。
- 与 superpowers 约束的候选表述保持一致：`You may use superpowers, but do not write any spec or plan.`

初步判断：需在 Phase 2 明确“短提纲”和“spec/plan 文件”的边界。

## 13. 第一性原理是推理约束，不是口号替代

候选 Skill 应要求从研究问题、原始输入、显式约束和可验证证据出发；现有模板只能加速表达，不能替代对数据、参数和输出的判断。

初步判断：这是用户明确要求，应保留为稳定约束；后续需把它转化为可执行检查，而不只是固定句子。

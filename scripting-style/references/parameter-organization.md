# 参数组织

## 分类

先区分参数的角色：

1. **路径参数**：输入对象、metadata、结果目录和文件名。
2. **运行参数**：线程数、批大小、随机种子和缓存开关。
3. **方法参数**：PC 数、resolution、模型选项和算法控制量。
4. **科学决策**：QC cutoff、目标细胞、marker、root/terminal、lineage、
   gene set 和 ligand–receptor。

路径和运行参数可集中在脚本前部。方法参数与科学决策应在首次使用前容易定位，并附上当前
任务的理由。

## 路径锚点与迁移

- 先确认 repository 或 runner 规定的 working directory，再定义路径。
- 项目内部输入、输出、脚本和资源使用相对于该锚点的路径，并在脚本头部说明锚点。
- 同一脚本不要无说明地混用 repository-relative、task-relative 与 script-relative 路径。
- 不硬编码 `/home/...`、用户目录、Windows drive path、`~` 或绝对 `setwd()`。
- 项目外部声明输入由 CLI 参数或项目已有 manifest / runner 契约提供；不要为了相对化而
  复制 source data，也不要在脚本里建立新的机器路径表。
- `normalizePath()`、`Path.resolve()` 等可用于运行时检查或审计，但解析结果不写回源码或
  可迁移配置。

## 放置规则

- 多处复用的值在前部定义一次。
- 路径值使用同一已说明锚点下的相对形式。
- 只影响单一步骤的值放在该步骤附近。
- 参数名表达含义和单位，避免 `x1`、`tmp2` 一类名称。
- 输出文件名由阶段、对象和比较维度构成，不与输入覆盖。
- 一组相互依赖的参数放在一起，并在注释中说明关系。
- 不为少量参数引入 YAML、TOML、环境变量层或配置 class。

## 参数依据

对会改变解释的参数，至少说明一种依据：

- 当前数据分布或诊断图；
- 方法文档或已知约束；
- 预先定义的研究设计；
- 与 baseline 或替代值的比较；
- 用户明确指定的生物学假设。

无法确定时，把候选值和需要检查的证据写清楚，不要照搬范例历史值。

## 推荐形式

```r
# 根据 elbow 与批次分离诊断选择；不要从其他项目照搬
n_pcs <- TODO_N_PCS

# 研究设计预先定义的比较
stage_levels <- c("TODO_EARLY", "TODO_LATE")
```

模板中的 `TODO` 必须在交付前替换。若当前任务不需要某项参数，删除它而不是保留空配置。

## 自检

- 参数是否在使用前可见？
- 路径锚点是否明确，源码是否没有机器特定绝对路径？
- 科学决策是否与普通运行参数混在一起而失去解释？
- 是否存在没有依据的历史默认值？
- 是否为了参数组织引入了超过任务规模的工程结构？

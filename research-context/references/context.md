# 上下文恢复与更新

项目只维护一份 `context.md`。它是压缩后的当前状态，不能替代被引用的证据。后续工作实际依赖某个结果时，读取相应产物及必要说明，不仅依赖 Agent 的转述。

## 恢复

遵循项目已有指令，读取唯一的 `context.md`。沿用用户指定位置；未指定时，已有的 `docs/context.md` 是约定入口。结合当前用户请求识别活动问题，再按摘要中的入口定向读取必要的数据说明、代码、产物或其他材料。入口缺失或过时时，围绕当前问题查找和核实。

发现摘要与其他来源冲突时，先判断冲突属于哪一类：

- 实际输入、输出或检查结果：核对相关产物、代码及执行记录，区分当前版本与旧版本。
- 解释或推断：保留依据、假设和不确定性，不因文件较新就认定解释成立。
- 人的决定：以用户明确作出的决定为依据。产物或测试结果不能自行撤销研究取舍；新证据需要改变取舍时，提交用户判断。

报告影响当前工作的冲突并更新已核实的摘要；不能确认的内容标明待核实，不静默覆盖。

入口不存在时不自动创建。能够开展的工作继续，并说明哪些状态尚未持久化。

## 保存内容

沿用已有文档格式，以足够简短的内容回答：

| 内容 | 恢复工作时需要知道什么 |
| --- | --- |
| 目标与当前问题 | 用户要解决什么，现在具体追问什么 |
| 当前进展 | 做到了哪里，哪些事实已核实，哪些解释仍是暂定的 |
| 输入与产物入口 | 当前使用哪些文件或对象，必要的版本或处理状态是什么 |
| 关键决定 | 用户已决定什么、为什么；Agent 的建议是否仍待决定 |
| 未决问题与探索分支 | 有哪些限制、反例、冲突、待比较方案或阻塞 |
| 下一步 | 做什么、为什么做、需要先满足什么条件 |

这些是信息要求，不是强制模板或字段合同。简单项目无需空章节。大型项目也只维护这一份摘要，通过路径引用详细材料。

保留会影响后续判断的失败、反例、方向修正，以及方案被放弃的简短理由和重新考虑的条件。不要因某个结果不显著、与主解释冲突或暂时未被选择，就把它从可恢复的上下文中抹去。

原始终端日志、长篇调试过程、完整数据表、整段搜索结果、重复内容和无关尝试不写入摘要。已持久化的细节用入口替代；压缩信息时保留判断依据，不只留下结论。

## 更新时机与责任

输入或产物改变、获得重要观察、用户作出决定、研究方向调整、发现影响下游的问题时，由 Main Agent 更新发生变化的摘要内容，不逐条命令记录。

切换任务、中断、总结或交接前，保存尚未记录的重要进展、未完成工作及恢复入口。无实质变化时不重写；更新时注明时间，旧状态被取代后保留仍有决策价值的原因与引用。

Main Agent 统一维护 `context.md`。Sub-agent 返回建议更新项，不直接编辑共享摘要。
